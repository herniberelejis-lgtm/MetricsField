Sacar Next.js: qué hay, qué cambia y cuánto sale

Para David. No es urgente y no bloquea el lanzamiento del 17 — es la evaluación técnica para que la decisión se tome con números reales delante, no con la idea de que es "cambiar un framework por otro".

Base: main, commit reciente ~13.000 líneas de TypeScript Esfuerzo estimado: 6 a 10 semanas

La aclaración que cambia toda la pregunta

Next.js ya corre sobre Node. No hay "Next" de un lado y "Node" del otro — Next es un framework que se ejecuta con Node como runtime. Ahora mismo, cuando alguien entra al portal, es Node el que procesa ese request, con las reglas de Next puestas encima (rutas por carpeta, Server Components, Server Actions).

Así que "pasar de Next a Node" en la práctica es: sacar el framework Next.js y armar un servidor Node propio (Express o Fastify) con un frontend React aparte, que le pida datos por HTTP. Es un proyecto real, del tamaño de una reescritura de arquitectura — no un cambio de dependencia en package.json.

No es que el código esté mal escrito

El propio CLAUDE.md lo dice explícito: "Sin ORM ni API REST separada — Server Actions, no endpoints. Los formularios llaman funciones "use server" directamente." Esa es la apuesta arquitectónica central del producto: sin Next, esa apuesta desaparece y hay que reemplazarla por otra (API + frontend separados), que es un patrón distinto de punta a punta, no una variación del mismo.

02

Qué hay que cambiar

Cinco frentes de trabajo, cada uno con su propio riesgo de romper algo.

1Las 33 Server Actions → endpoints REST

Hoy un formulario del portal llama directo a una función del servidor. En Node puro hay que envolver cada una en una ruta (POST /api/comercios/:id, etc.), armar el cliente HTTP del lado del frontend, y manejar a mano los estados de carga y error que hoy Next resuelve solo con useTransition.

El más grande de los cinco, en volumen de código a tocar.

218 páginas dinámicas → modelo API + SPA

Cada página hoy trae sus datos en el servidor antes de renderizar (así /portal/[codigo] arma todo el HTML con los datos ya adentro). En Node + React puro, el navegador pide el HTML vacío y después pide los datos por separado — más lento en la primera carga, salvo que armes SSR a mano, que es otro proyecto adentro de este.

3Middleware, cookies y sesión

lib/sesion.ts está escrito a propósito para correr en dos runtimes (Node y Edge) con una sola implementación, porque divergir ahí es exactamente el tipo de bug que abre un agujero de seguridad. Sacando Next, todo pasa a Node — en rigor se simplifica, pero hay que tocar el archivo más sensible del repo con cuidado.

4El cron diario

Hoy Vercel llama /api/cron/sync-google solo, todos los días. Sin Vercel, hay que armar ese disparador en otro lado (GitHub Actions con un schedule, o un proceso propio) y seguir protegiéndolo con CRON_SECRET como ahora.

5Deploy y hosting

Se pierde el deploy automático por rama (preview por PR) que da Vercel gratis. Hay que elegir dónde corre el servidor Node (Railway, Render, un VPS propio) y armar ese pipeline de cero.

03

Lo que NO cambia

Vale decirlo porque es lo que hace que esto sea factible y no una locura.

Toda la capa de datos

lib/db.ts y sus 65 funciones son SQL directo contra Postgres, sin nada de Next adentro. Se mueven prácticamente intactas a cualquier backend Node.

Las 8 rutas de app/api/

Los callbacks de OAuth, el cron y la descarga de QR ya son HTTP puro — reciben un Request y devuelven un Response. Se portan a Express casi sin tocar nada.

Toda la lógica de negocio y seguridad

PIN con scrypt, cifrado AES-GCM, validación de URLs, rate limit distribuido: nada de eso depende de Next. Los 36 tests de seguridad siguen pasando sin cambios.

React, TypeScript, Tailwind

Los 33 componentes de components/ son React normal. Se reusan en el frontend nuevo — cambia cómo reciben los datos (por fetch en vez de props del servidor), no cómo se ven.

04

Dónde se puede romper algo

Los mismos principios de la sección de refactors del plan de la semana, aplicados a un proyecto más grande.

El riesgo real no es que algo deje de andar

Es que algo siga andando pero mal, y nadie lo note porque no tira un error — muestra un número equivocado. Al mover 33 Server Actions a endpoints REST, es fácil que un formulario mande el dato viejo mientras el nuevo carga, o que dos requests en paralelo pisen el resultado del otro. Hoy Next lo maneja solo; en Node puro, hay que manejarlo a mano en cada uno de los 33 casos.

Los puntos más delicados, concretamente:

  • El star-gate. El código que manda a todos al mismo link de Google, sin filtrar por calificación, hoy vive en un Server Component simple. Al reescribirlo como endpoint, cualquier cambio en el orden de validación puede reintroducir sin querer un desvío — exactamente lo que el proyecto tiene prohibido por ley de marca.
  • Las cookies de sesión. lib/sesion.ts firma con HMAC y valida en tiempo constante. Reescribir el guard de Node hay que hacerlo con la misma lógica exacta, o se abre una ventana de sesión inválida aceptada.
  • El rate limit. Hoy corre igual en el middleware de Edge y en las Server Actions porque comparten una sola implementación. Separado en Node puro, hay que asegurarse de que las dos puntas sigan usando el mismo store de Upstash.

Cuánto tiempo, con qué hecho antes

El rango depende de una sola variable: si hay tests antes de empezar.

Sin esa red, a pulmón 10+ semanas, con riesgo real de bugs silenciosos en producción Cada uno de los 33 endpoints y las 18 páginas se verifica a mano, mirando la pantalla — se pasan por alto los casos borde.

Con el equipo completo dedicado full-time sería el número de abajo del rango; a medio tiempo, alternando con el trabajo comercial del día a día, el de arriba. En ningún escenario es una tarea de días.

06

Si el objetivo real es otro

A veces "sacar Next" es la forma de pedir algo más chico. Vale la pena chequear cuál de estos es el motivo real antes de emprender la reescritura grande.

Motivo
"No queremos depender de Vercel"
Solución chica
next start en un servidor Node propio (Railway, Render, un VPS). Seguís usando Next — no se toca una línea de app/ ni lib/. Se pierde el cron nativo y el deploy por rama, que se reemplazan con GitHub Actions.
Motivo
"Quiero una API REST separada para conectar otra cosa" (una app móvil, un tercero)
Solución chica
Exponer endpoints nuevos en app/api/ — que ya es HTTP puro, como muestra la sección 03 — sin tocar las Server Actions existentes. Las dos cosas conviven en el mismo Next.
Motivo
"El equipo se siente más cómodo con Express/Node puro que con las convenciones de Next"
Solución chica
No hay atajo — es el escenario real de este documento. Pero vale la pena separarlo de los dos de arriba, porque es una preferencia de equipo, no una limitación técnica del producto.

Antes de empezar cualquiera de los tres

Preguntá cuál de los tres es. Los primeros dos se resuelven en días sin abrir este documento. El tercero es este documento entero.

07

Recomendación

Es factible y no hay nada en el código actual que lo impida — la capa de datos, la seguridad y los componentes de UI se llevan casi intactos. Pero es 6 a 10 semanas de un equipo que hoy es de dos personas de código, en un producto que recién esta semana empieza a vender.

Mi sugerencia: no lo agenden todavía. Que este documento quede como referencia, y se retome después de que:

  1. El producto tenga sus primeros diez clientes pagando — recién ahí una decisión de arquitectura de dos meses tiene contexto real de qué está funcionando y qué no.
  2. La red de tests de negocio esté puesta (la que David arma esta semana) — reduce el escenario de 10+ semanas al de 6-8.
  3. Se haya confirmado con quien lo pidió cuál de los tres motivos de la sección 06 es el real — puede que la necesidad concreta se resuelva en días, no en meses.
